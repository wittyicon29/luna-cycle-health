# Luna Health: owner setup guide

The steps only the owner can do (accounts, identity, keys, money, legal choices), in the order
that avoids waiting. Each step says what to decide, what is recommended and why, and what to hand
to engineering afterwards. Facts about the repository were checked on `main` at commit `73a0733`.
External facts were checked on **2026-11-10** and carry their source; where something could not be
confirmed without logging in, the text says **verify in the console**. Prices are rough estimates,
not quotes.

Rules that apply throughout:

- This is a personal project. Use only accounts, domains and addresses you personally own. Never
  use an employer's domain, Google Cloud organisation, Play account, e-mail or ids.
- No secret goes into the repository, a chat, a ticket or CI. Secrets go into your password
  manager first, then onto the server or build machine (see [6](#6-secrets-inventory-handoff)).
- Placeholders used here: `<app ID>`, `example.com`, `api.example.com`, `app.example.com`,
  `owner@example.com`, `support@example.com`.

## 1. Android application ID

### 1.1 Decide

The application id (package name) identifies the app on Google Play and on every phone. **It can
never change once the app is created in Play Console** (`billing-owner-checklist.md` 1.1; Play
treats a different id as a different app). It must be reverse-domain style, lowercase, segments
starting with a letter, only `a-z`, `0-9`, `_` (`scripts/android/rename-app-id.sh` enforces this
and rejects Java keywords, `com.example.*` and the placeholder).

| Option | Example | When to use |
| --- | --- | --- |
| **Reversed domain you own (recommended)** | domain `example.in` → `in.example.luna`; `example.com` → `com.example.luna` (illustration only; `com.example.*` is refused by the script) | You own (or will buy) a personal domain. Best long-term signal of ownership; the same domain can host the API, the web pages and the support mailbox |
| GitHub-style | `io.github.<username>.luna` | Only if you own that GitHub username. Hyphens are not allowed: `my-name` becomes `my_name` |
| Anything else | | Avoid names you do not control. Never an employer's domain |

Recommendation: buy the domain first (step 5.2), then use its reversed form plus `.luna`. Keep
the id boring: it is visible in the Play URL (`play.google.com/store/apps/details?id=<app ID>`),
so a discreet id such as `in.example.luna` is better than one containing "period".

### 1.2 Apply it in the repo (engineering can run this once you give the id)

```bash
bash scripts/android/rename-app-id.sh <app ID>
cd frontend && npm run android:sync
```

Files that contain the placeholder `app.placeholder.luna` today (`git grep -l app.placeholder.luna`):

| File | What changes | Changed by the script? |
| --- | --- | --- |
| `frontend/capacitor.config.json` | `appId` | Yes |
| `frontend/android/app/build.gradle` | `namespace`, `applicationId` | Yes |
| `frontend/android/app/src/main/res/values/strings.xml` | `package_name`, `custom_url_scheme` | Yes |
| `frontend/android/app/src/main/java/app/placeholder/luna/MainActivity.java` | `package` line, directory moved | Yes |
| `frontend/android/app/src/main/java/app/placeholder/luna/LauncherAppearancePlugin.java` | `package` line, directory moved | Yes |
| `frontend/android/app/src/main/assets/capacitor.config.json` | generated copy (not tracked) | Yes, and regenerated by `android:sync` |
| `scripts/android/release.sh`, `scripts/android/rename-app-id.sh`, `scripts/android/test-release-guards.sh` | The placeholder is the value they guard against | **No, keep** |
| `frontend/android/README.md` (discreet-mode `adb` commands) | Documentation | No (docs are never edited by the script); update by hand if wanted |

Outside the repository, the id must also be entered in:

- Play Console when creating the app;
- `GOOGLE_PLAY_PACKAGE_NAME` in `deploy/.env` (billing verification, `backend/app/core/config.py`);
- the **Android OAuth client** in Google Cloud (package name + SHA-1, step 3), which is why the id
  must be final before Google sign-in can work in release builds;
- the `<your app ID>` commands in `offline-emulator-checklist.md` when you run it.

There is no `google-services.json` or Firebase project in this app (the Gradle file only applies
the plugin if such a file exists), so nothing to change there.

## 2. Google Play Console

### 2.1 Account type: personal or organisation

Sources: "Required information to create a Play Console developer account"
(<https://support.google.com/googleplay/android-developer/answer/13628312>), "Get started with Play
Console" (<https://support.google.com/googleplay/android-developer/answer/6112435>), both checked
2026-11-10.

| | Personal | Organisation |
| --- | --- | --- |
| Needs | Legal name and address (from your Google payments profile), contact e-mail and phone, developer e-mail | A legal entity with a **D-U-N-S number** (free, "can take up to 30 days"), organisation website, phone |
| Shown publicly on Google Play | Developer name, legal name, country, developer e-mail. **"If you decide to monetize on Google Play then Google will display your full address."** | Legal name, legal address, developer e-mail and phone |
| Testing before production | **12+ testers opted in to a closed test for 14 continuous days** (accounts created after 2023-11-13) | Not required |
| Device check | Must verify access to an Android device with the Play Console mobile app | (verify in the console) |
| Fee | US$25 one-time (no prepaid cards) | Same |

**Decision point: your home address.** Luna sells a subscription, so a personal account will show
your **full address** on the listing. Options: (a) accept it; (b) use an address you are allowed to
use as your legal address, such as a business address or a registered office (whether a virtual
office address is accepted: **verify in the console**; Google may check it against your
payments profile); (c) form a legal entity and open an organisation account (D-U-N-S, more cost
and paperwork, no 14-day testing rule). Recommendation: for a personal project, a personal account
with option (b) if your home address must stay private; otherwise (a). Decide before
registering, because the legal address comes from the payments profile you link.

### 2.2 Register

1. Use a Google account that you personally own, protected with 2-step verification and a
   hardware key or authenticator app. Consider a dedicated account (for example
   `owner@example.com`) so the developer account does not depend on your everyday mailbox.
2. Go to <https://play.google.com/console/signup>, choose **personal**, pay US$25 with a non-prepaid
   card in your legal name, complete identity verification (government ID may be requested,
   answer/6112435).
3. Install the Play Console app on an Android phone and complete the device verification.
4. Set up a **payments profile / merchant account** for India (needed to sell the subscription;
   bank account and tax details: **verify in the console**).
5. Check the Play Console Home page for any "Android developer verification" or app registration
   task: Google's 2026 developer verification programme registers Play apps automatically in most
   cases, with enforcement starting 2026-09-30 in some countries
   (<https://android-developers.googleblog.com/2026/06/android-developer-verification.html>, found via
   search 2026-11-10; **verify in the console**).

Calendar time: identity and payments verification can take days (exact duration not published:
**verify in the console**). Start this first.

### 2.3 Create the app

Only after the application id is final (step 1):

1. **Create app**: name "Luna Health" (or the chosen listing title), default language English
   (India) or English (United States), App, Free.
2. Fill **Policy > App content** and **Store listing** from `store-prep.md` sections 1, 2 and 5.
3. Package name is bound at the first bundle upload; it must be the final `<app ID>`.

### 2.4 Play App Signing (on by default)

Source: <https://support.google.com/googleplay/android-developer/answer/9842756> (checked
2026-11-10). New apps are enrolled by default: Google keeps the **app signing key** (signs what
users install), you keep an **upload key** (signs what you upload). A lost upload key can be reset
by Google; a self-managed app signing key cannot. Recommendation: let Google generate the app
signing key; you only create the upload key (step 4). The page also mentions "quantum-ready hybrid
signing" with up to three fingerprints for hybrid-signed apps: register every SHA-1 the App
signing page shows with the OAuth client (step 3).

### 2.5 Testing tracks

Source: <https://support.google.com/googleplay/android-developer/answer/9845334> and
<https://support.google.com/googleplay/android-developer/answer/14151465> (checked 2026-11-10).

| Track | Who | Use for Luna |
| --- | --- | --- |
| Internal testing | Up to 100 testers by e-mail; builds arrive within minutes | You and engineering: first builds, billing tests with license testers, pre-launch report |
| Closed testing | E-mail lists or Google Groups | **The mandatory 12-tester / 14-day test** for a personal account. Use a Google Group so testers can join with one link |
| Open testing | Anyone can join from Play | Optional; not needed |
| Production | Everyone in the selected countries | After "Apply for production" is approved (review "usually takes seven days or less") |

Closed-test tips: recruit **15-20** testers so you stay above 12 if some opt out (opting out and
back in restarts their 14 consecutive days, answer/14151465). Testers need an Android phone and
must install from the opt-in link and stay opted in. Ask them to actually use the app (log a
period, a few check-ins, reminders, offline) and send feedback; the production application asks
about the closed test.

### 2.6 Subscription products

Exactly as `billing-owner-checklist.md` 1 requires (the app maps the period from the base plan id):

- [ ] Product `luna_ai_monthly`, one base plan id `monthly` (or `p1m`), auto-renewing, INR price.
- [ ] Product `luna_ai_yearly`, one base plan id `yearly` (or `p1y`), auto-renewing, INR price.
- [ ] Optional free trial: one new-customer free-trial offer per base plan, nothing else.
- [ ] Base plans activated.
- [ ] Setup > License testing: add every tester account that will test purchases.

Service fee for auto-renewing subscriptions in markets such as India: 15 %
(<https://support.google.com/googleplay/android-developer/answer/112622>, checked 2026-11-10).

### 2.7 Service account and API access for the backend

As `billing-owner-checklist.md` 2:

1. In your own Google Cloud project (step 3 uses the same project), create a service account and
   a JSON key; save the key in your password manager, never in the repo.
2. Enable the Google Play Android Developer API in that project.
3. Play Console > Users and permissions: invite the service account e-mail; grant view financial
   data and manage orders and subscriptions for this app.
4. Hand over: the JSON file goes to the server as `deploy/secrets/<file>.json` (readable by uid
   10001), `GOOGLE_PLAY_SERVICE_ACCOUNT_FILE` points to its in-container path,
   and uncomment the `./secrets/play-service-account.json:/run/secrets/...:ro` volume line in
   `deploy/compose.prod.yml` (lines ~97-98), `GOOGLE_PLAY_PACKAGE_NAME=<app ID>`, `BILLING_PRODUCT_IDS=luna_ai_monthly,luna_ai_yearly`,
   `BILLING_ACCOUNT_SECRET` (`openssl rand -hex 32`, set once, never change), then
   `BILLING_MODE=google`.

Permission changes can take time before verification calls succeed (billing checklist 2.4).

## 3. Google OAuth clients

Google sign-in uses the native Credential Manager flow through `@capgo/capacitor-social-login`
(`frontend/src/nativeGoogle.js`): the app asks Google for an ID token whose audience is the **Web
client ID**; Google checks the calling app by **package name + SHA-1** registered on an **Android
client**; the backend accepts the token only if its audience is listed in
`GOOGLE_ID_TOKEN_AUDIENCES` (`backend/app/core/config.py`, `backend/app/services/google_id_token.py`).

### 3.1 Steps (Google Cloud Console, your personal project)

1. Create a project (for example "luna-health"), owned by your personal account. The same project
   holds the Play service account (2.7).
2. **Google Auth Platform / OAuth consent screen**: user type External; app name "Luna Health";
   support e-mail `support@example.com`; developer contact `owner@example.com`; app home page
   `https://app.example.com`; privacy policy `https://app.example.com/privacy`; terms
   `https://app.example.com/terms`; authorised domain `example.com`.
3. **Scopes**: only `openid`, `email`, `profile` (the app requests `email` and `profile`).
   These are basic identity scopes: test users are not limited to the 100-user test list and see
   no unverified-app warning even while the app is in Testing; any other scope removes that
   exception (<https://support.google.com/cloud/answer/15549945>, checked 2026-11-10). Click
   **Publish app** to move to "In production" before launch anyway. Showing your logo/app name
   may require brand verification (**verify in the console**).
4. **Create a Web application client.** No redirect URI needed for the Android app. Its client
   id is the "Web client ID".
5. **Create an Android client** for `<app ID>` with each SHA-1 that will sign an installed app:
   - the **app signing key** SHA-1(s) from Play Console > Test and release > App integrity > Play
     app signing (only available after the app exists in Play Console; Play installs need it);
   - the **upload key** SHA-1 (`keytool -list -v -keystore <upload keystore>`), for locally
     built release APKs;
   - the **debug keystore** SHA-1 (`keytool -list -v -keystore ~/.android/debug.keystore -storepass android`),
     for engineering's debug builds.
   One Android client per package name/SHA-1 pair, or several fingerprints where the console
   allows (as described in `frontend/android/README.md` "Google sign-in").
6. Optional, web only: the backend also has a redirect-based web flow
   (`backend/app/services/google_oauth.py`) that reads `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`
   and `GOOGLE_REDIRECT_URI` from the environment (not listed in `deploy/.env.example`). It is
   only needed if Google sign-in should work on the website. Recommendation: leave it unset at
   launch; the web frontend is needed for legal and e-mail-link pages only.

### 3.2 Map to configuration

| Value | Where it goes | Secret? |
| --- | --- | --- |
| Web client ID | `GOOGLE_ID_TOKEN_AUDIENCES` in `deploy/.env` (comma-separated if several) **and** `REACT_APP_GOOGLE_WEB_CLIENT_ID` at build time (`frontend/src/config.js`; `release.sh` refuses to build without it unless `LUNA_ALLOW_NO_GOOGLE=1`) | No (public identifier), but keep it in the password manager entry for completeness |
| Android client | Nothing in the repo; Google matches package name + SHA-1 | No |
| Web client secret (only if 3.1 step 6 is used) | `GOOGLE_CLIENT_SECRET` in `deploy/.env` | **Yes** |

Order dependency: the app signing SHA-1 exists only after the app is created in Play Console, so
Google sign-in on Play-installed builds works only after step 5 is repeated with it. Test
email/password sign-in first.

- [ ] Consent screen complete, published
- [ ] Web client created, id handed over
- [ ] Android client with debug + upload SHA-1 (before first internal build)
- [ ] App signing SHA-1(s) added after app creation

## 4. Release keystore and Play App Signing

### 4.1 Create the upload key (once, on your own machine)

From `frontend/android/README.md`, with a stronger key size than the 2048-bit minimum Play
accepts for upload keys (answer/9842756):

```bash
keytool -genkeypair -v -storetype PKCS12 \
  -keystore ~/luna-upload.keystore \
  -alias luna -keyalg RSA -keysize 4096 -validity 10000
```

- Run it **outside the repository** (`.gitignore` ignores `*.keystore` and `*.jks`, but do not rely
  on that).
- Use long random passwords (store password and key password; with PKCS12 they are normally the
  same). Put both in the password manager before you close the terminal.
- The certificate's name fields (CN, O, ...) are visible to anyone who inspects the APK: use your
  own name or the app name, never an employer.

### 4.2 Store and back up

- Two independent copies: password manager attachment plus an encrypted offline copy (for
  example an encrypted USB drive kept elsewhere). Never in the repo, cloud chat, e-mail or CI.
- Record the SHA-1 and SHA-256 (`keytool -list -v -keystore ~/luna-upload.keystore -alias luna`)
  in the same password manager entry.
- If the upload key is lost or leaked: Play Console > Play app signing > "Request upload key
  reset" with a new key's PEM certificate (answer/9842756). Users are not affected because the
  app signing key stays with Google. Then update the Android OAuth client SHA-1.

### 4.3 How the release build uses it

`frontend/android/app/build.gradle` reads the signing configuration from the environment only;
`scripts/android/release.sh` checks everything and runs `./gradlew bundleRelease`:

| Variable | Meaning |
| --- | --- |
| `LUNA_KEYSTORE` | Path to the keystore file (must exist) |
| `LUNA_KEYSTORE_PASSWORD`, `LUNA_KEY_ALIAS`, `LUNA_KEY_PASSWORD` | Passwords and alias |
| `LUNA_VERSION_CODE` | Positive integer, new and higher for every upload |
| `LUNA_VERSION_NAME` | User-visible version, letters/digits/`.`/`_`/`-` |
| `REACT_APP_API_BASE` | Must be `https://...` |
| `REACT_APP_GOOGLE_WEB_CLIENT_ID` | Web client ID (step 3) |
| `REACT_APP_SUPPORT_EMAIL` | Support address shown in the Privacy Policy and Terms (`frontend/src/config.js`); not checked by `release.sh`, so do not forget it |

Enter passwords without leaving them in the shell history:

```bash
export LUNA_KEYSTORE=~/luna-upload.keystore LUNA_KEY_ALIAS=luna
read -rs LUNA_KEYSTORE_PASSWORD && export LUNA_KEYSTORE_PASSWORD
read -rs LUNA_KEY_PASSWORD && export LUNA_KEY_PASSWORD
LUNA_VERSION_CODE=1 LUNA_VERSION_NAME=1.0.0 \
REACT_APP_API_BASE=https://api.example.com/api/v1 \
REACT_APP_GOOGLE_WEB_CLIENT_ID=<web client id> \
REACT_APP_SUPPORT_EMAIL=support@example.com \
bash scripts/android/release.sh
```

Output: `frontend/android/app/build/outputs/bundle/release/app-release.aab`. Note the
`REACT_APP_API_BASE` value includes `/api/v1` (the web app appends paths to it, and the Privacy
Policy derives the `/account-deletion` link by stripping `/api/v1`, `frontend/src/legalContent.js`).

Who builds: if engineering builds releases, they need the keystore and passwords on their build
machine; the alternative is that you run `release.sh` yourself. Recommendation: you build releases
(the upload key never leaves your machine), engineering prepares the commit and tag.

## 5. Hosting, domain, e-mail and providers

### 5.1 Hosting the Docker stack

The production stack (`deploy/compose.prod.yml`) is Postgres 16, Redis 7, a migration job, the
API and Caddy on **one Linux server with Docker Engine 25+**, ports 80/443 only, IPv4 only
(`deploy/README.md`). It does **not** yet serve the web frontend; engineering must add that
(store-prep 7.3 item 4), and it can run on the same server.

| Option | Fit | Rough monthly cost (estimate, verify current prices) |
| --- | --- | --- |
| **VPS (recommended)** with 2 vCPU, 4 GB RAM, 50-80 GB SSD, Ubuntu 24.04 LTS, in an Indian region (providers with Mumbai/Bengaluru/Delhi regions exist; check availability on the provider's site) | Runs the stack unchanged; full control; backups via `scripts/backup_db.sh` | about US$6-25 for the server, plus US$1-5 for off-site object storage for backups |
| PaaS (container platforms with managed Postgres/Redis) | Needs rework: no Caddy, managed database instead of the `db` service, different backup story; the scripts in the runbook would not apply as written | about US$20-60+ |
| Managed Kubernetes | Overkill for one API | higher |

Recommendation: a VPS in India. Reasons: the stack and runbook were written for it, latency for
Indian users, and a simpler privacy story ("hosted in India", if you choose such a region). Data
location is also a privacy-policy statement (store-prep 4.2), so decide it before the policy is
finalised. Check that the provider offers full-disk encryption or encrypted volumes if you want to
claim more than the field-level encryption the app already does.

Server checklist (details in `deploy/README.md` "First deploy"):

- [ ] SSH key login only, password login off, firewall: TCP 22, 80, 443 and UDP 443 only.
- [ ] Automatic security updates on.
- [ ] Provider account with 2-step verification; billing alerts.
- [ ] Off-site backup bucket at a **different** provider, with write-only credentials for the
      server if supported (runbook 4.1).

### 5.2 Domain and DNS

- Buy a domain you will keep (roughly US$10-20 per year for common TLDs; estimate). The same
  domain serves the app id (step 1), the API, the web pages and e-mail.
- Suggested names: `api.example.com` (API), `app.example.com` (web frontend: privacy, terms,
  verify-email, reset-password).
- DNS: **A records only** pointing at the server's IPv4 address. **Do not add AAAA records**: the
  stack is IPv4 only and IPv6 clients would all share one rate-limit bucket (`deploy/README.md`
  "IPv4 only").
- TLS: nothing to buy. Caddy obtains and renews certificates automatically once the A record
  resolves; set `API_DOMAIN` and `ACME_EMAIL` in `deploy/.env`.
- Turn on registrar lock and 2-step verification at the registrar; losing the domain would break
  sign-in links, the privacy URL and e-mail.

### 5.3 E-mail (SMTP) for verification and password reset

The API sends verification and reset e-mails over SMTP (`SMTP_SERVER`, `SMTP_PORT` 587 STARTTLS,
`SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME` in `deploy/.env.example`); sign-up
cannot complete without it (login is refused until the address is verified).

- Choose a transactional e-mail provider that offers SMTP submission and lets you authenticate your
  own domain. Costs are typically free to about US$15/month at launch volumes (estimate).
- Use a sending subdomain or address such as `no-reply@example.com`; set up at the DNS provider:
  - **SPF** (TXT record from the provider),
  - **DKIM** (the provider's CNAME/TXT keys),
  - **DMARC** (`_dmarc` TXT, start with `p=none` and a report address you control, tighten later).
- Gmail requires all senders to have SPF or DKIM, valid reverse DNS and TLS, and bulk senders (over
  5,000 messages a day) SPF, DKIM and DMARC (<https://support.google.com/a/answer/81126>, checked
  2026-11-10). Doing all three from day one is cheap and keeps verification mail out of spam.
- The provider receives users' e-mail addresses: name it in the privacy policy (store-prep 4.2)
  and check its data-processing terms and data location.
- Set up the **support mailbox** `support@example.com` (`SUPPORT_EMAIL` on the server,
  `REACT_APP_SUPPORT_EMAIL` in the build, Play listing contact). It receives deletion and grievance
  requests: make sure someone reads it.

### 5.4 AI provider accounts

Both are optional for launch (without keys, chat fails with a friendly error and Insights returns
the fallback), but the Luna AI plan sells exactly these features, so do not enable
`BILLING_MODE=google` without them.

**Groq** (chat, and the second step of Insights; `GROQ_API_KEY`, `QWEN_MODEL`):

- Create an account with your personal e-mail and 2-step verification; create an API key; set a
  spending limit if offered.
- **Enable Zero Data Retention** in Data Controls. Groq states that by default it does not retain
  inference data, but may log inputs/outputs up to 30 days for reliability or abuse investigations
  unless ZDR is on, and that customer data is stored in Google Cloud buckets in the United States
  (<https://console.groq.com/docs/your-data>, checked 2026-11-10).
- Check in the services agreement / DPA: no training on your inputs, retention, sub-processors,
  transfers from India. The data page did not state the training position.

**Hugging Face** (first step of Insights; `HUGGINGFACE_API_KEY`, `MEDGEMMA_MODEL`):

- Create an account and a fine-grained token with permission to call inference
  (<https://huggingface.co/docs/inference-providers/index>, checked 2026-11-10).
- The model `google/medgemma-1.5-4b-it` may require accepting its licence/terms on its model page
  (**verify on the model page**).
- Concern for engineering: the code calls the old `api-inference.huggingface.co` host, which
  community reports say now returns 410 in favour of `router.huggingface.co` (store-prep 7.3 item 7).
  If it fails, the MedGemma step is skipped silently (`llm_service.py`: empty medical analysis) and
  Groq still writes a report from statistics alone, so the user is not told. Official Hugging Face docs (<https://huggingface.co/docs/inference-providers/providers/hf-inference>, checked 2026-11-10) say HF Inference now focuses on CPU models and list no text-generation task, so MedGemma is likely not served there at all. Options: a third-party provider that serves it (named in the policy), a dedicated Inference Endpoint, or dropping the step.
  Through the router, requests can be served by third-party inference providers, each with its own
  data terms: find out which provider would serve the model and read its terms before the privacy
  policy names the recipient.

### 5.5 Error reporting (optional)

`SENTRY_DSN` empty = off (the default; the SDK is not even loaded). When set, only unhandled
server exceptions are sent, scrubbed to exception class, stack frames and request id
(`backend/app/core/error_reporting.py`, `deploy/.env.example`). Options: Sentry SaaS (choose a
region) or self-hosted GlitchTip (Sentry-compatible; another service to run and back up).
Recommendation: launch with it **off** and rely on the uptime checks in runbook 8; if you turn it
on, add the provider to the privacy policy and revisit the Data safety "Diagnostics" answer.

### 5.6 Legal review

Book a lawyer familiar with Indian privacy law (Digital Personal Data Protection Act) to review the
Privacy Policy, Terms, consent texts and the account-deletion page (store-prep 3 and 4). Lead time
is outside engineering's control; start early. This guide does not give legal advice.

when the accounts exist (this guide does not edit the runbook):

| Item | Where it is used | What breaks if lost | Notes |
| --- | --- | --- | --- |
| Google account owning Play Console and Google Cloud | Everything Google | Account recovery can take long; the app cannot be updated meanwhile | 2-step verification, recovery codes stored offline |
| Domain registrar and DNS provider logins | DNS, e-mail authentication | Domain hijack or expiry breaks API, links, e-mail | Registrar lock, auto-renew |

| E-mail provider login (and SMTP credentials) | `SMTP_*` | Verification/reset mail stops | Already partly in runbook (`SMTP_PASSWORD`) |
| Groq and Hugging Face logins | `GROQ_API_KEY`, `HUGGINGFACE_API_KEY` | AI features stop | Keys already in runbook |
| `GOOGLE_CLIENT_SECRET` (only if the web Google flow is enabled) | `deploy/.env` | Web Google sign-in stops | Rotate in Google Cloud |
| Upload keystore SHA-1/SHA-256 and alias | OAuth Android client | Nothing (reference data) | Store next to the keystore entry |
| Reviewer test account password | Play App content > App access | Review blocked | Rotate after review if shared widely |

Hand over to engineering, by a channel you trust (not the repository, not this chat): values for
`deploy/.env` that you generated, the service-account JSON file, and (only if engineering builds
releases) the keystore. Everything else they need is non-secret and listed in [7.2](#72-what-i-need-from-you).
